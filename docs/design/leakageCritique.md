# Adversarial Review: AlphaForge Designs A/B/C

## CRITICAL findings

**1. Survivorship bias in the backfill candidate set — the "survivorship-bias-free" guarantee is hollow for pre-go-live delistings.**
SEVERITY: critical. Location: Design A §4.1 (`list_instruments(): Current exchange metadata`) and §6.2 ("Bars of delisted instruments are never deleted"; "`rebuild_history` ... regenerates an unbiased history").
Why wrong: the lake is seeded from `list_instruments()`, which returns only *currently listed* markets. Every perp Binance delisted before the system is built (LUNA, FTT, SRM, TORN, BTS, COCOS, dozens more) never enters the lake at all, so `rebuild_history` ranks a candidate set that already survived to 2026. "Never delete bars of delisted instruments" only protects against delistings *after* go-live. The 2020–2026 backtest universe is survivorship-biased from day one — exactly the long-bias inflation Design A claims to prevent, and its own gate ("at least one historically delisted symbol appears in past membership") will pass only for symbols delisted after backfill starts running, giving false comfort.
Fix: seed instruments from a historical listing source, not the live endpoint: Binance delisting announcements / archived `exchangeInfo` snapshots (Wayback), Binance Vision data dumps (delisted symbols' klines remain downloadable), or a vendor list. Add a regression test asserting specific known pre-2026 delistings (e.g., FTTUSDT perp) appear in 2021–2022 membership. Until then, stamp every backtest report "universe survivorship-biased before <go-live date>".

**2. μ unit contradiction at the B→C interface — 72× position-scaling error.**
SEVERITY: critical. Location: Design B §9.2 / §4.4: `μ_{i,t} = IC_target · σ̂_{i,t}·sqrt(h) · F̃ · G_t` with h=72; predictions schema: "`mu` float64 (expected return **over horizon**)". Design C §6.2: "Contract with the ML/alpha layer: it delivers **per-bar** expected returns `r̂_bar,i`; we annualize `μ_ann = r̂_bar × 8760`."
Why wrong: B hands over a 72-bar-horizon expected return; C multiplies it by 8760 instead of 8760/72 — a 72× inflation of every μ. C's own safeguard (#4, ex-ante-vol assert 0.01–2.0) will NOT catch it: the constraint box (gross ≤ 1.0, w_max, turnover cap) clips the solution into a plausible-looking portfolio that is actually "max out everything the alpha sign says," with the cost penalty effectively zeroed relative to μ. Backtest behaves like an unregularized signal-chaser; the failure is silent.
Fix: make the contract explicit and tested: B emits `mu_ann_{i,t} = μ_h · (8760/h)` (or `mu_bar = μ_h/h`), field named `mu_ann`; C consumes it verbatim. Add a boundary unit test: feed a synthetic signal with known IC through SignalService → optimizer and assert resulting ex-ante alpha (μᵀw) is in a plausible band; add `assert np.abs(mu_ann).max() < ~3.0`.

**3. Two parallel, incompatible feature frameworks (and two cores) — the anti-skew machinery guards the wrong path.**
SEVERITY: critical. Location: Design A §7 (`features/spec.py` FeatureSpec, FeatureContext, FeatureEngine.compute_history/compute_asof, parity.py, `src/alphaforge/features/...`) vs Design B §2.1 (`alphaforge/features/base.py` Factor protocol taking a raw panel, FactorRegistry, FeaturePipeline, SignalService with its own "rolling buffer"). Also: A `core/instruments.py` Instrument (with fees, SCD2) vs C `core/types.py` Instrument (different fields); A `core/calendar.py` TradingCalendar vs C `core/calendar.py` BarCalendar; A pydantic Settings vs C `core/config.py`; fees in A's instruments table vs C's `FeeSchedule` presets.
Why wrong: same package path, colliding module names, incompatible abstractions. If B's pipeline + SignalService is what actually computes live signals, then A's PIT reader, FeatureContext windowing, `compute_asof` parity test, and `code_hash` cache invalidation protect code that isn't on the live path — train/serve skew (Design A's risk #5) returns through the back door. Two Instrument models and two fee sources guarantee drift (e.g., A's SCD2 fee changes never reach C's cost model).
Fix: one feature framework (A's Context/engine, since it carries the PIT and parity machinery), with B's factor math implemented as registered features; B's SignalService must call `FeatureEngine.compute_asof`, not its own buffer. One `core/` owned jointly: single Instrument, single calendar, fees read from A's SCD2 instruments table by C's `TransactionCostModel`. Make `af features parity` and B's truncation test run on the *deployed* path.

**4. Vectorized research engine fills at the decision-bar close — all sweeps, variant selection, and the PBO input matrix inherit same-bar lookahead.**
SEVERITY: critical. Location: Design C §5: `r_p(t) = Σ W[t-1]·R[t] − TC(t)`, "Documented biases: fills at close t (not open t+1)".
Why wrong: the weight decided at close t−1 is assumed on at the *exact close print used to compute the signal* — zero-latency execution. For 1h mean-reversion (B's `mr_res_24` is a primary factor) this is precisely where the fake edge lives: you buy the reversal *at* the extreme close. Thousands of variants are screened on this engine, and §7.3's PBO matrix is built from these returns — so the survivors are selected partly *for* their close-fill artifact, and the "research gate" certifies the artifact. The parity test (one momentum strategy, corr > 0.99) does not cover reversal variants, where the divergence concentrates.
Fix: vectorized engine must use the same timing as the event engine — it's equally vectorizable: `r_p(t) = Σ W[t-2]·R_oo[t]` with open-to-open returns, or shift weight application one full bar. Extend the parity CI test to include a 24-bar reversal strategy with an explicit acceptance band. Build the PBO matrix only from timing-correct returns.

**5. Quality-flag lookahead: `BAD_PRINT_SUSPECT` is computed from `close_{t+1}` and then drives the default feature NaN policy at bar t — and the design's own anti-lookahead tests cannot catch it.**
SEVERITY: critical (sneaky, rare-event, systematically favorable). Location: Design A §5.2 condition 3 ("Reversion: |ln(close_{t+1}/close_{t-1})| < 0.5·|r_t|"), §5.3 ("default policy: treat BAD_PRINT_SUSPECT closes as NaN then forward-fill ≤ 2 bars").
Why wrong: the flag on bar t encodes information from bar t+1. Research features computed later see the upgraded flag and NaN-out the spike; live at time t sees only `OUTLIER_RETURN` (conditions 1–2) or nothing. So research quietly erases exactly the adverse prints that live trading eats — e.g., a flash-wick that stops you out lives in production but is ffilled away in backtest. Crucially, both the parity test and the truncation-invariance test read the *same stored flags*, so both pass while the leak persists. Flags are also retroactively "upgraded/cleared next day," mutating the effective history.
Fix: give each flag bit its own `available_at` (BAD_PRINT_SUSPECT available at `ts_open + 2Δ`), have the PIT reader mask flag bits by availability, and restrict the feature-layer NaN policy to bits available at decision time. Re-run truncation tests *with flag recomputation inside the truncation*.

## MAJOR findings

**6. Funding interval hard-coded at 8h — many Binance perps fund every 4h (some 1h).**
SEVERITY: major. Location: Design B §2.5 ("settles every 8h", `CARRY = −f̄·3·365`); Design C `BarCalendar.funding_ts_in` ("00:00/08:00/16:00 UTC"); Design A instruments has `funding_interval_hours` but nobody consumes it.
Why wrong: Binance moved many alt perps (precisely the rank-20–40 names in `perp_top40`) to 4h funding. C's backtest applies funding only at 8h boundaries → up to half the funding cashflows on those names are silently dropped (cost optimism on shorts-pay regimes, fake alpha on carry trades). B's `×3×365` annualization is off 2× for 4h contracts, corrupting the carry factor's cross-sectional ranking (8h vs 4h symbols mis-scaled relative to each other).
Fix: apply funding in the backtest by iterating the *funding events table* (Design A already stores actual `ts_funding` per symbol), never a clock; annualize carry per symbol as `−f̄ · (8760/funding_interval_hours)` from the instruments table. Property test: total funding applied == sum of stored funding events over the position's holding intervals.

**7. Execution-timing skew: backtest fills at the next bar's open print; live fills ≥ 20s grace + compute + submit after the open.**
SEVERITY: major. Location: Design C §9.2 (`grace_s=20`, then reconcile → ingest → features → model → optimizer → orders) vs §4.2 NextOpenFill (`P = open_{t+1}·(1+s·(hs+impact))`); Design A γ=30s; Design B "entry price ... O_{t+1}".
Why wrong: live market orders land ~1–3 minutes after the bar boundary. For momentum-conditioned orders the drift between open print and arrival is adverse in expectation (you buy what just went up). This latency cost is in no model, and it compounds with finding 15 (the loop wakes before the data is even written).
Fix: add a latency term: fill at open + κ·σ_1h·sqrt(latency/3600) in the signal's direction, calibrated from paper-trading arrival-price data; log decision_ts, submit_ts, fill_ts and report arrival slippage vs bar open weekly. Until calibrated, use a conservative fixed add-on (e.g., +2bps) in both engines.

**8. Cost-model "validation" during paper trading is circular.**
SEVERITY: major. Location: Design C §8.2 ("PaperBroker ... `price = cost_model.fill_price(...)` — identical TransactionCostModel") and §13.3 ("weekly live report comparing realized fill slippage vs modeled slippage").
Why wrong: paper fills are generated *by* the model, so realized-vs-modeled slippage compares the model with itself and will show perfect agreement for the entire paper phase. The 2.5bps half-spread and Y=1.0 impact coefficient go to "real money" untested.
Fix: at each submission, snapshot the actual order book (free via ccxt `fetch_order_book`); fill paper orders by walking the book; compare walked-book cost vs model cost — that's a genuine validation signal in paper mode. Also persist top-of-book spread per symbol to populate the half-spread override table with measured values (2.5bps flat is optimistic for rank-30–40 alts in stress).

**9. One 60-day validation tail triple-used: early stopping + isotonic calibration + champion/challenger promotion — and the champion already consumed most of it.**
SEVERITY: major. Location: Design B §6.2 ("early-stopping validation = final 60d ... then isotonic calibrator on val") and §6.4 ("promoted only if, on the shared validation tail...").
Why wrong: (a) iteration count, calibration map, and the promotion decision are all fit/selected on the same 60d window — val metrics are optimistically biased and the calibrator is fit on data the ES procedure already optimized against; (b) the incumbent champion (trained 7d earlier) used ~53 of those 60 days as *its* early-stopping/calibration set, so the "shared" comparison window is unseen by neither model. The promotion gate is a noisy, contaminated comparison performed 52 times a year — a slow selection ratchet.
Fix: split the tail (e.g., 40d ES / 20d calibration), and gate promotion only on data strictly after both models' fit windows (the live week(s) since the champion was trained — true out-of-sample for both). Track cumulative promotion decisions as trials in the DSR N.

**10. Multiple-testing N for DSR excludes the vectorized prescreen — N is measured, but measured wrong.**
SEVERITY: major. Location: Design B §7.4 ("`N` = number of strategy configurations actually tried (logged automatically ... every **CPCV run** appends its config hash)") + Design C §5 ("fast factor research sweeps (**thousands of variants**)").
Why wrong: selection pressure is applied at the vectorized-sweep stage; only survivors reach CPCV. If N counts only CPCV runs, the expected-max benchmark SR* is computed over dozens of trials when thousands were actually tried — DSR is overstated, the ≥0.95 gate is too easy. This is the precise failure mode DSR exists to prevent.
Fix: log every vectorized variant's config hash into `experiments.log` too; N = all distinct configs evaluated anywhere in the funnel (or estimate effective N via the correlation-clustering procedure from Bailey–LdP). Also feed the *sweep-stage* return matrix to PBO, not just the CPCV finalists.

**11. Triple-barrier label economics are gross-of-everything and gap-blind; meta-P(win) sizes trades whose net edge is negative.**
SEVERITY: major. Location: Design B §5.2 ("Exit prices at the barrier level itself ... assumes a resting limit/stop fill at the barrier"), §5.3 (`y_meta = 1{s·ret > 0}`).
Why wrong: (a) stops gap through barriers in crypto — assuming exit at the barrier price flatters every stop-out; (b) PT assumes a touch (`high ≥ up`) fills a limit, optimistic when high == barrier; (c) `ret` excludes fees, spread, and ~9 funding settlements over a 72-bar hold — for a 1σ_H barrier (a few %), 15–25bps round trip + funding is a material fraction of the edge. The classifier learns P(gross win); bet sizing then deploys capital on configurations that lose net. The conservative both-touch rule does not offset this.
Fix: label on cost-adjusted return: `ret_net = ret − roundtrip_cost_frac − E[funding over hold]·sign` using C's `TransactionCostModel` (one import — the design's own "single cost model" doctrine); fill stop exits at min(barrier, next bar open) when the bar gaps; keep the gross label as a diagnostic only.

**12. The model predicts outcomes of a trade lifecycle (PT/SL barrier trades) that the deployed policy never executes.**
SEVERITY: major. Location: Design B §5–§6 (barrier-event classifier → bet size) vs Design C §6 (hourly MVO re-optimization, 10% turnover cap, no PT, 2.5σ *daily*-vol backstop stop ≠ 1.0σ_72h barrier).
Why wrong: research statistics live in label space (hit rates, barrier outcomes, calibration); production PnL is generated by a continuously rebalanced portfolio with totally different exits. Nothing forces the two to agree; a model that looks great on barrier labels can be neutral-to-negative under the MVO policy (and vice versa). This is train/serve skew at the *policy* level.
Fix: the only deployment gate must be the C-engine walk-forward of the full pipeline (B signals → optimizer → fills) — make this explicit and gate on it (DSR/PBO computed on *that* return stream); treat label-space metrics as model-development diagnostics only. Reconcile stop conventions (either implement barrier exits in execution, or drop them from the narrative of expected behavior).

**13. HMM gate timing for intraday use unspecified — filtered-on-the-current-day is still lookahead.**
SEVERITY: major. Location: Design B §8: filtered `P(s_t|x_{1:t})` on *daily* observations; "`G_t` multiplies the final μ vector" applied at hourly bar closes.
Why wrong: the design correctly avoids smoothing, but never states which day's posterior gates hour h of day d. Using day-d's observation (return/vol of the day in progress) is lookahead; it's the natural off-by-one when joining daily probs to an hourly grid. Also `hmmlearn.GaussianHMM` has no `n_init` parameter — restarts must be hand-rolled, or the spec silently won't do what it says.
Fix: define `G` for all hours of day d as the filtered posterior through day d−1's close (available 00:00 of day d, +grace); enforce with a merge_asof on an explicit `available_at = day_close + lag`. Implement restarts as an explicit loop over seeds keeping best LL.

**14. CPCV embargo (168 bars) is far shorter than the longest feature lookback (2160 bars).**
SEVERITY: major. Location: Design B §7.1 ("Default E = 168 bars (7d) — > 2× the 72-bar max label horizon, with headroom for serial correlation in features") vs §2.3 (`mom_xs_2160_168`, 90d lookback; β window 720; RVP 8760).
Why wrong: in CPCV, train samples starting 8 days after a test block compute their 90d momentum, 30d betas, and 1y vol-percentile mostly from *test-block prices*, creating strong train/test dependence that purging by `t1` doesn't touch. The "headroom" claim is wrong by an order of magnitude for the slow features. CPCV Sharpe/IC distributions — the input to PBO and model selection — are inflated.
Fix: at minimum run an embargo-sensitivity study (E ∈ {168, 720, 2160}) and report degradation; structurally, prefer embargo ≈ the dominant feature decorrelation length, or restrict CPCV inference to the fast-feature model and rely on the strictly forward-chaining WF (where this cannot occur) for anything with slow features.

**15. Scheduling race: live loop wakes before the data layer has written the bar.**
SEVERITY: major. Location: Design C §9.2 `next_cycle_ts(..., grace_s=20)` vs Design A §3.3 "runs at floor(now,Δ)+γ, γ = 30,000 ms" plus fetch/validate/write time.
Why wrong: every hour the loop's stage-1 "confirm bar present" check fires ~10+ s before the updater even *requests* the bar. Best case the cycle stalls/retries hourly; worst case a permissive fallback uses the previous bar — features one bar stale in live but fresh in backtest, a systematic live-vs-research drift that nobody will see in any test.
Fix: single shared config constant; loop grace = updater grace + p99 write latency + margin (e.g., 90s), or better, event-driven: updater touches a per-bar "ready" marker (or notifies via the heartbeat table) and the loop blocks on it with a timeout → staleness path.

**16. Two walk-forward/purge implementations with conflicting parameters and a retrain-cadence mismatch.**
SEVERITY: major. Location: Design B `validation/splits.py` (purge by `t1` intersection + 168-bar embargo, 90d tests) vs Design C `analytics/walkforward.py` ("purge_days=5, embargo_days=1", 30d tests); Design B §6.4 live retrain = weekly vs C's WF model swap = every 30d.
Why wrong: the "deployment-faithful final evaluation" (B §7.1) and the "stitched OOS equity curve" (C §10.4) use different purging math and different refit cadence than production (weekly). Duplicate implementations of the integrity-critical splitter is exactly how a purging bug ships in one of them; and a 30d-refit backtest neither over- nor under-states a weekly-refit live system in a knowable direction.
Fix: one splitter library (B's, with `t1`-aware purging) imported by C's runner; set WF test_days=7 to match the weekly retrain (or change live retrain to 30d); assert shared horizon/embargo constants from one config — Design C already gestures at this ("asserted equal, not duplicated") — make it real for *all* parameters.

**17. Cross-design data-contract contradictions (timestamps, bar labeling, identifiers, schemas).**
SEVERITY: major. Location: A §0 ("integer epoch-milliseconds", bars labeled by **open**) vs B conventions ("datetime64[ns, UTC]", `ts` = bar start) vs C ("integer epoch **seconds** ... always refer to **bar close**"); C also mixes units internally (`Fill.ts_ms` vs `cycle_ts` in seconds). Identifiers: A `"BINANCE:PERP:BTCUSDT"` vs B `"BINANCE:BTC/USDT:USDT"` vs C `"BTC/USDT:USDT"`. Columns: A `instrument_id`/MultiIndex vs B `symbol` long format + `in_universe` bool (A's DatasetBuilder instead *drops* out-of-universe rows — B's CS pipeline needs the mask, not pre-dropped rows). Parquet: A zstd/year-partitioned vs B snappy/month-partitioned. Funding: A `ts_funding`+`available_at`; B `ts` only.
Why wrong: open-labeled-ms joined to close-labeled-s is a one-bar lookahead (or lag) at every interface, the single most common way these systems silently break; identifier mismatches cause silent inner-join row loss that looks like "missing data."
Fix: Design A's contract wins (it's the most rigorous): everything downstream consumes `(ts_open ms UTC, instrument_id)` + derived decision time via one helper; B and C revise to it; add an integration test that round-trips one bar through ingest → features → signal → backtest fill and asserts the fill bar opens exactly at decision time.

## MINOR findings

**18. Funding availability off-by-one-settlement between A and B.** Location: A §3.2 (`available_at = ts_funding + 5 min`) vs B §2.5 ("`f_{τ_j}` enters ... only for `τ_j ≤ t`"). At t = 16:00 the just-settled rate is visible under B's rule, invisible under A's. Fix: B joins on A's `available_at` column, full stop.

**19. Blend-weight degenerate case.** Location: B §9.1: `w_k = max(ÎC_k,0) + κ, κ = 0.2·mean_k max(ÎC_k,0)`. If all EWMA ICs ≤ 0, all weights and κ are 0 → 0/0 on normalization. Fix: `κ = max(0.2·mean(...), κ_floor)` with absolute floor; fall back to equal weight + alert.

**20. `lookback_bars` decoupled from params.** Location: A §7.2: `ret_log` registered with `lookback_bars=2` but `window` is a free param. A `window=24` spec under-loads the live buffer (caught only as NaN-vs-value parity failure, at runtime). Fix: `lookback_bars` must be a function of params (`spec_factory(params) -> lookback`), validated at spec construction.

**21. Universe rebalance live/backtest race.** Location: A §6.1 `effective_from = rebalance_ts` (membership flips at the 00:00 decision instant) vs `update_current` running inside the live cycle. If universe update runs after stage-3 signals on the 1st of the month, live trades the old universe for one cycle while the backtest assumed the new one. Fix: pin ordering in the cycle (universe update before signals) or set `effective_from = rebalance_ts + Δ`.

**22. Spot+perp collinearity in the optimizer.** Location: A ingests both markets; C `shortable_i` distinguishes them; nothing prevents BTC spot and BTC perp both entering the optimization. Near-singular Σ → unstable basis-trade weights; vol-target sees ~zero ex-ante vol on the pair and scales up (capped at s_max but still). Fix: v1 tradable universe = perps only (it's named `perp_top40`); if spot enters later, add a per-base combined-exposure constraint.

**23. Cross-sectional event redundancy unweighted.** Location: B §5.4 ("concurrency is computed within symbol; cross-symbol commonality is handled by CV purging"). Purging removes train/test overlap; it does nothing about ~40 simultaneous, regime-correlated events per bar inflating effective N inside training and validation statistics. Fix: multiply sample weights by `1/√n_t` (events at t) or report cluster-bootstrapped (by timestamp) error bars on IC/logloss.

**24. Vertical-barrier exit at `C_{t+H}` is unobtainable.** Location: B §5.2 ("if no touch: exit_price = C_{i,t+H}"). The label exits at a close you only know at exit-decision time; the consistent convention (which B itself imposes on entries) is `O_{t+H+1}`. Small but directional with momentum signals. Fix: vertical exits at next open, matching §5.1.

**25. Champion HMM/retrain/universe/quality job orchestration never unified.** Weekly retrain Sun 00:30 (B), HMM refit 1st of month (B), universe rebalance 1st 00:00 (A), batch quality "next day" flag upgrades (A), daily tearsheet 00:05 (C) — five schedulers across three designs with no shared ownership. Fix: one scheduler/cron table in the live loop with explicit dependency ordering.

**26. HMM data-availability claim inconsistent.** B §8 sizes identifiability on "~2500 daily observations (2019→)"; A's `backfill_start = 2020-01-01`. Minor: recompute the parameter-count argument on actual data, or extend backfill.

**27. Fee/half-spread defaults never reconciled with A's SCD2 fee columns** (folded into #3, but specifically: BNB-discount, VIP-tier changes recorded by A's SCD2 will never propagate to C's frozen `FeeSchedule` presets). Fix: cost model reads fees through the instruments store with `as_of`.

**28. ffill of flagged closes dampens vol estimators.** A §5.3 default policy (NaN→ffill ≤ 2 bars) injects zero returns into B's EWMA σ̂, slightly deflating barrier widths and vol-target inputs after every flagged print. Acceptable if rare — but monitor count, and exclude ffilled bars from σ̂ updates instead.

**29. Documented-but-real residual approximations** (all minor because disclosed): VaR `sqrt(24)` iid scaling under vol clustering (C §7.2); funding mark = close proxy (C §4.3); LW shrinkage intensity derived for iid sample cov applied beside an EWMA S (C §6.1); hourly Sharpe autocorrelation inflation (C §10.1). Fix: keep the daily-aggregated Sharpe cross-check as the headline number; report VaR also on overlapping 24h returns.

## The 5 fixes that matter most

1. **Kill the survivorship hole at the source (Finding 1):** backfill from a historical listing/delisting record (Binance Vision dumps + announcement archive), not `list_instruments()`; regression-test that known pre-go-live delistings appear in historical membership.
2. **Fix the μ contract (Finding 2):** B emits `mu_ann` (= horizon-μ × 8760/h), C consumes it verbatim; add a B→C boundary unit test and a μ-magnitude sanity assert in the optimizer.
3. **One code path, one core (Findings 3, 16, 17, 27):** single feature framework (A's engine + parity/truncation tests on the *deployed* path), single Instrument/calendar/fee source, single purged splitter shared by B's CV and C's walk-forward, single timestamp convention (`ts_open`, ms, UTC).
4. **Remove same-bar fills from the research funnel (Findings 4, 10):** vectorized engine executes at next open like the truth engine; extend parity CI to a reversal strategy; count every swept variant in the DSR trial count N and feed sweep returns to PBO.
5. **Make funding and labels cost-honest (Findings 6, 11):** apply funding from the per-symbol funding-events table (4h/8h aware) in both engines, annualize carry by actual interval; meta-label on cost-and-funding-adjusted returns with gap-aware stop exits.
